核验日期：2026-10-18（UTC）。任务：`dashboard-research-20261018 / memberships`。LifeOS 基线：`dba64cb0181bde7e8dc1f1610263d9a2c6983267`。本报告是研究与实施输入，未实现会员模块，也不代表已验收或上线。

关联：[LifeOS #27][i27]、[LifeOS #9 会员需求][i9]、[HuangYincan/idea #4][idea]、[本地编辑与导出 #31][i31]。已读取上述 Issue 的正文及全部评论。遵循用户本次“先详尽调研、完善 Issue，再开发”的顺序；本文不单独修改 Issue，由协调者汇总发布。

## 1. 结论与已有决定

会员模块适合作为综合看板中的一个业务视图。用户已经在 #9 要求参考 Wallos 的代码逻辑，重写为符合 OS 风格的应用；本次又明确与个人状况、自建服务、服务器探针合并。idea #4 中“需求不足以支撑独立产品”的判断不阻止这个方向，也不要求重新验证一款独立商业产品才能开发。

应参考成熟实现的分类、周期、预计费用、管理入口和提醒思路，但重新定义三个相互独立的事实：**权益是否有效、未来是否计划续费、是否实际付款**。自动推进日期不是付款证据，关闭自动续费不等于权益立即终止，打开取消链接不等于已经取消。这些约束已经存在于 idea #4，而非本次新增产品方向。[idea][i9]

首个实施阶段建议完成 OS 原生界面中的本地私有建档、处理队列、确定性计算、付款确认和导出。公开网站只接收主动选择的公开快照；常在线通知服务、银行或邮箱自动发现、自动取消、家庭多人协作、截图识别留到独立后续任务。该顺序符合 #31 当前“本地编辑 → 导出 → 审查 → Pages 发布”的决定，不能把接口预留或本地定时器写成已经上线的通知能力。[i31]

## 3. Wallos 源码核验：可以参考什么，哪些规则需重新定义

### 3.1 金额、周期与支付方式

`endpoints/subscription/add.php` 保存 `price`、`currency_id`、`frequency`、`cycle`、`next_payment`、`auto_renew`、`start_date`、`payment_method_id`、付款人和分类、`inactive`、`cancellation_date`、备注和 URL。金额绑定为 `SQLITE3_FLOAT`。其中支付方式是标签/图标等元数据；`endpoints/payments/add.php` 实际插入 `payment_methods`，不能因目录名为 payments 就当成付款流水。[w-add][w-payment]

`getPricePerMonth` 的周期约定是日付按 `30 / frequency`、周付按 `4.35 / frequency`、月付按 `1 / frequency`、年付按 `1 / (12 × frequency)` 折算；一次性购买返回 0。年度费用为月均乘 12。`storetotalyearlycost.php` 定时保存当前活跃订阅的年化总额，所以成本趋势图是**估算快照趋势**，不是逐笔支付历史。[w-stats][w-history]

LifeOS 可借鉴“原币 + 周期 + 折算值”的显示，但需改用可精确运算的金额表示、固定并说明折算规则。一次性购买的“无持续月均”不应被呈现成“这笔购买免费”。

### 3.2 自动推进与手动续费

`updatenextpayment.php` 选择已过期、`auto_renew = 1`、`inactive = 0` 的记录，用 `DateInterval` 连续加周期，再更新 `next_payment`。`renew.php` 处理 `auto_renew = 0` 且非一次性购买的记录，至少推进一期并推进到未来。上述两个接口没有生成付款确认对象。[w-roll][w-renew]

因此 `auto_renew` 在这里还承担“应用自动推进排期”的作用。LifeOS 不能把它直接映射为“服务商自动扣款已确认”，也不能将“手动续费按钮完成”自动等同于真实扣款成功。用户主动确认的付款，应单独记录发生时间、原币金额及确认来源。

### 3.3 不能把一条日期算法概括成整个项目

同一 Wallos 提交中存在两条不同的路径：上述 cron/手动接口直接调用日期区间加法；`includes/budget_period_calculations.php` 的 `shiftSubscriptionOccurrence` 则在月/年周期保留锚定日，并截断到目标月份可用日期。`getSubscriptionOccurrencesInRange` 枚举期间内的事件，`computeAmountNeededInPeriod` 累计这些事件；非自动续费记录只计当前一次计划。新期间预测并非简单拿月均值乘月份。[w-period]

这说明应统一 LifeOS 的排期、日历、提醒与费用预测算法，避免多个页面各自算日期。不能从一条旧函数直接声称 Wallos 所有月份都算错；本次没有运行其 PHP 环境来验证每条组合行为。

### 3.4 停用、取消与试用

Wallos 本次核验的写入路径主要用 `inactive` 和 `auto_renew` 表示活动/推进状态；`replacement_subscription_id` 用于替代订阅比较。`cancellation_date` 被取消提醒任务用作“当天应提醒处理”的日期，筛选仍活跃且非一次性记录，不能解读为已经完成取消。写入模型没有独立的试用结束、权益终止、暂停恢复或促销后价格字段。[w-add][w-cancel]

LifeOS 必须允许“已取消未来续费，权益仍有效”，并把试用价格与转正价格分开。暂停不会自动推迟权益到期；恢复也不能悄悄补记暂停期间每笔付款。是否延期、退款或恢复原账期需要用户确认服务商的实际规则。

### 3.5 汇率与通知的边界

`wallos_convert_price` 使用用户所属汇率表并按 `price / rate` 换算；找不到汇率或汇率为空/零时返回原数值。不能在 LifeOS 复制这种数值回退：若直接汇入另一币种总额，会隐藏单位不一致。应保留原币、列出缺失项，并显示“不完整估算”。[w-rates]

Wallos 的续费通知按 `notify_days_before` 或全局提前天数匹配当天日期；取消提醒匹配 `cancellation_date` 当天。仓库 cron 按实例时区安排每天任务。渠道实现和测试接口很多，但所读调度路径不是持久化 outbox：不能据此承诺离线补发、逐渠道幂等或到达用户设备。Webhook 路径检查 HTTP 状态；所读 ntfy 路径仅依据 cURL 是否返回 false 显示发送结果，说明“命令成功、服务接受、设备收到”必须分层核验。[w-notify][w-cancel][w-cron]

## 4. 其他实现给出的补充约束

SubsTracker 的 `newSubscription` 记录名称、类别、起始/到期日期、周期、提醒、启停、自动展期与农历选项。没有金额、币种和已支付对象。创建/编辑时会把过去的到期日期循环推进到未来，所读这两段逻辑没有按 `autoRenew` 排除；定时检查另按 `autoRenew` 决定展期。这提示导入历史记录时必须保持原始日期，不能把“修正过期”作为隐式保存副作用。[s-code]

其通知逻辑在提前窗口内或非自动续费已过期时发出通知；当前检查路径没有写入逐事件通知去重记录。整份数组由读取、修改后 `KV.put`，读失败回退空数组。这些代码可以帮助列出测试场景，但 LifeOS 应明确报读取错误、使用版本冲突控制，避免错误时显示“空清单”或并发覆盖。[s-code]

SubTrackr 的 `Autopay *bool` 明确区分未知、开启、关闭；状态包含暂停与试用。提醒记录同时包含上次发送时间、对应续费日及已触发窗口。`GetStats` 先累计 `TotalsByCurrency`，换算失败设置 `ConversionComplete = false` 并返回原币分组，过期汇率另标时间，值得作为缺失处理的正向参考。[t-model][t-service]

SubTrackr 同时提供版本化日期算法：模型包含按原始账单日截断到月末的路径，也有从上一次截断结果继续推进的路径；`AfterFind` 对 Active 记录会写入新的续费日。不能只凭 `NoOverflow` 函数名认定所有月末、闰年都保留原始锚点。LifeOS 应显式存锚点，并从锚点计算第 N 次事件；读取接口不写回业务状态。[t-model]

## 5. 建议领域模型：先拆清事实，再形成表单

下表是供综合看板 PRD 采用的建议，不宣称现有 LifeOS 已有这些实体。共享身份、持久化和公开投影由平台任务统一定义；会员模块不另建用户体系。

| 对象 | 建议数据 | 关键不变量 |
| --- | --- | --- |
| `Membership` | 稳定 ID、服务/套餐名称、分类、可选服务资产引用、说明、来源和最后核对时间 | 同一服务可有多个套餐；合并提醒不合并不同账号的权益；默认私有 |
| `Entitlement` | 有效起始/结束、试用结束、有效/试用/暂停/结束/待确认、赠送或附带权益说明 | 权益事实与未来付款安排分离；未知结束时间不填一个虚构日期 |
| `RenewalPlan` | 自动扣款 `on/off/unknown`、计划 `active/paused/cancelled/unknown`、下一次预计日期、周期与原始锚点、已知后续价格、最晚处理时间、付款渠道、管理 URL | 关闭扣款与停止续费计划是两个字段；手动续费也可能有预计支出；取消已确认后不生成未来续费事件 |
| `PaymentRecord` | ID、会员 ID、确认的原币金额、发生日期/时刻、确认时间、用户手动确认或可信导入来源、可选对应周期 | 只有明确确认才能进入实际已支付；日期推进不能生成；重复提交幂等；纠正记录保留可追溯关系 |
| `DecisionRecord` | 继续/暂停/取消/稍后、记录时间、目标计划、处理结果及确认时间 | “想取消”“打开页面”“已确认取消”是不同状态；最终状态修改必须明确确认 |
| `Money` / `RateSnapshot` | 原币与精确十进制字符串（或小单位整数字符串）、汇率基准/目标币种/倍率/日期/来源 | `null` 表示未知，`0` 表示确定免费；金额、倍率不能用展示字符串或二进制浮点累计 |
| `ReminderEvent` | 会员/计划版本、事件种类、目标日期、提前量、处理状态；后续服务阶段再加渠道投递记录 | 续费、权益到期、试用结束、取消截止各自建事件；已取消计划的旧事件不可继续投递 |

不要用一个超大的 status 枚举穷举所有组合。表单可以显示“已取消续费 · 权益至 2026-12-31”，底层分别保存计划与权益状态；后台投影保证组合合法。付款人和权益使用者可以不同，首版保留成本归属说明，不扩展为多人账户系统。

自建服务、域名或 VPS 若已有服务资产记录，会员项只关联其 ID 和费用安排，不重复保存 IP、密钥或探针配置。综合概览聚合事件与经过授权的摘要；费用只由会员模块的一份计划贡献，避免服务卡片和订阅卡片重复相加。

## 6. 时间与金额规则

### 时间

- 将业务日期保存为经过日历校验的 `YYYY-MM-DD`，配合明确的 IANA 业务时区；将真实发生时刻保存为带偏移/UTC 的时间戳。仅有日期的账单不能先当成 UTC 零点再按浏览器时区转换，否则用户换时区可能看到前一天。
- “权益有效至某日”在首版明确定义为该业务时区当日结束时仍有效；若服务商提供精确失效时刻，单独使用精确时间字段。缺少具体时间的取消截止必须标为日期级信息，不能显示伪精确小时倒计时。
- 月周期保留原始日号，计算第 N 个目标月，再将日号截断到该月末；后续月份继续用原始日号。合成例：2027-01-31 → 2027-02-28 → 2027-03-31。季度是 3 个月，不是 90 天。
- 年周期保留原始月日，缺失日期截断到对应月末；合成例：2024-02-29 的年付计划在 2025 年为 02-28，到 2028 年恢复 02-29。日/周周期按业务时区的日历日推进，不以固定毫秒数替代跨夏令时的一天。
- 一次性、终身与赠送权益可以没有续费周期；不自动推算下一次扣款。周期数量必须为正整数且有支持的单位，非法日期与循环上界错误明确拒绝。
- 不长期修改“next date”以掩盖漏核对记录。根据锚点计算未来计划，同时保留已过的待确认事件。服务长期关闭后再次打开，实际已支付总额不因此增加。
- 默认预测区间明确为业务时区的 `[今天, 今天 + 30 个日历日)`；十二个月预测为 `[今天, 今天 + 12 个日历月)`。界面说明边界，避免“本月”和“未来 30 天”混用。

### 金额

| 名称 | 算法与展示 | 不确定项如何处理 |
| --- | --- | --- |
| 实际已支付 | 对明确确认、未作废的历史付款按发生时间与币种汇总；后续退款能力通过明确调整记录处理 | 无付款记录显示“尚未记录”，不由计划倒推；首版不自动推测税费、退款或账单结算汇率 |
| 未来预计支出 | 枚举窗口内仍有效的计划事件，逐笔使用该事件已知价格；可展开核对日期和原币 | 待确认续费、试用转正价格未知、已暂停但恢复日未知，单独计数；不能当作 0 或默认无限续费 |
| 月均折算 | `n` 月周期为 `价格 / n`；`n` 年周期为 `价格 / (12n)`。建议日/周采用明确的固定 365 天年化口径，再除以 12，计算中保留精度，最后展示时舍入 | 仅用于比较持续成本，不能称为当月实付；一次性/赠送附带权益显示“不计持续月均”；未定价记录不计入 |
| 年化估算 | `月均折算 × 12`，保持同一口径 | 与“未来十二个月逐笔预计”分开展示；有试用、促销、取消或有限期时通常不同 |
| 统一币种估算 | 先保留各币种小计，再按明确的汇率快照转换；显示来源、日期、缺失/过期提示 | 缺失或非法汇率不回退为 1，不把 USD 数值直接当 CNY；可显示已知部分加“另有 N 项未折算” |

上述日/周折算是**本报告建议的展示约定**，不是某服务商的计费规则；开发 spec 必须固定后再测试。首版也可以先只显示日/周原始周期和逐笔预计，不提供其月均折算，避免过早增加口径。月/年订阅、未来事件枚举和实际支付仍须可独立使用。

首期优惠、后续原价、免费试用和正式周期需要独立字段或有限的价格阶段。首版至少支持“当前已知金额、后续金额未知”，不能将免费试用金额 0 无限外推。附带权益不再次计费，家庭分摊不默认平均分；未确认个人承担额时只显示套餐总价与说明。

## 7. LifeOS 原生交互与数据边界

视觉遵循 [UI 规范](../../concept/design-system.md)，复用 `components/system/LifeOS/Surface.ts`、File Explorer 工具栏/地址栏、原生状态栏、系统字体、边框和滚动条。会员模块位于综合看板同一窗口内；不新增独立品牌侧栏、巨大统计装饰、移动端外壳或应用内系统设置按钮。

建议初始会员视图：工具栏提供新增、搜索、筛选与排序；紧凑概览显示待处理数、未来 30 天已知预计与未确认项；主区展示名称、权益状态、下一处理日期、原币金额/周期和确认状态。详情区提供来源/上次核对、管理入口、付款与决定记录。列表和日历共用计算结果；颜色之外同时显示文字状态。窗口缩窄时自然换行/滚动，沿用 OS 窗口规则。

配置时区、默认币种、通知服务等跨模块配置进入系统设置；日常新增、编辑和“记录处理结果”属于业务操作，可以留在综合看板。中文与英文的金额、日期显示由同一类型化值产生，不能随语言切换重新解析金额或清空未保存内容。

基线内 `server/README.md` 明确仍是本地 JSON 与内存会话服务；`deployment.ts` 仅有公开作品/作者快照路径。本次扫描没有现成会员业务模块。#31 的导出工作位于独立任务分支，Issue 评论中的验证不等于已进入本研究基线。会员数据后续应接入协调者统一的本地持久化/版本/导出契约，不直接扩展到线上管理服务。[i31]

隐私要求：

- 初始记录、金额、账号别名、付款方式、管理链接、付款确认和备注默认私有；不要求账户密码、银行凭据或银行卡完整信息。
- 公开投影是显式字段白名单。仅手动选中的会员可进入快照，公开名称、类别、说明、权益状态等字段也应能逐项预览；金额/日期如需公开由用户明确选择。公开总计只基于公开投影，不泄露隐藏记录数量或私有合计。
- Pages 构建只读取已提交且明确公开的 seed/媒体；本地私有目录、备份、日志、通知令牌和会话不得进入静态文件、源码、Issue 或 CI 产物。
- 私有迁移包与公开发布包使用不同用途标识和导入入口；私有包不能被静态构建接受。导入先校验格式、版本、日期、金额、重复 ID 和对象引用，展示预览，再按已有版本冲突规则写入。
- 管理链接只允许明确定义的安全协议；外链点击仅打开平台。初期图标用受控资源或本地上传，不自动把全部会员名称发给第三方图标/AI 服务。

## 8. 提醒分阶段交付

本地阶段可靠地完成“打开应用即可看见待处理事项”，展示计算时间和最后核对时间；应用关闭期间不能依赖网页定时器。可提供用户主动导出的日历事项作为补充，但日历客户端何时同步和是否提醒需要真实验证，不能称为 LifeOS 已送达通知。

引入常在线服务后，才能独立验收外部提醒。建议先一个用户确定的渠道，执行真实测试通知，保存发送尝试、提供方接受/失败和重试状态。事件去重键至少包含计划版本、事件类型、目标日期、提前窗口与渠道；多实例或任务重跑不能产生重复事项。修改日期/取消计划后撤销旧事件。错过发送时间应按固定补发窗口补发一次或显示已错过，不能无限重复催促。

发送失败不能把事项标为已处理；提供方返回成功不能标为用户已读。通知正文默认只含必要标题、事件时间和回到 LifeOS 的入口，金额/账号/备注由隐私选项决定。密钥仅保存在服务端配置，Webhook/自建通知地址的 SSRF 防护由统一连接器层承担。
