# 综合看板：个人活动、位置与健康调研

调研日期：2026-10-18（UTC）。关联 [LifeOS #37](https://github.com/Hi-Yincan/LifeOS/issues/37)；产品基线 `dba64cb0181bde7e8dc1f1610263d9a2c6983267`。本文是研究与实现建议，不是已经完成的设备接入、医疗评估或生产验收。

## 1. 需求与结论

#37 的[原始需求评论](https://github.com/Hi-Yincan/LifeOS/issues/37#issuecomment-6244732718)把个人状况分为两层：

1. 目前在做什么、每日安排、地理位置与每日轨迹。
2. 睡觉/起床时间、睡眠质量、心率、步数等高频健康指标，以及体检、血常规、视力等低频记录。

每个功能必须能单独选择是否向访客展示、展示多少天、延迟一天或一周等。用户设想持续在线的后端与智能穿戴设备同步。现有仓库生产仍为 Pages 静态访客模式，不能据此认为连续采集、私有存储、后台任务和公开撤回已具备。

建议把本模块划分为「活动与日程」「位置与轨迹」「日常健康」「检查记录」四个面板，共用数据来源、时间范围、同步状态与公开策略。活动采集优先研究 ActivityWatch，位置接入优先研究 OwnTracks 协议，已有轨迹库可适配 Dawarich；健康接入按用户设备选择 HealthKit 或 Health Connect 桥接。低频检查记录先支持人工确认的结构化记录和私有附件。不要把一个健身 App 或 PHR 系统整体搬入 LifeOS。

现有成熟项目能提供数据采集和业务规则参考，但尚未找到覆盖 #37 全部需求且天然满足 LifeOS 访客公开模型的单一实现。尤其不能把后台服务在线等同于手表持续采样、手机持续上传或秒级更新；必须分别展示测量时间、最后收到数据时间和来源状态。

## 3. 代表实现比较

### 3.1 ActivityWatch：自动活动记录

**可借鉴能力。** [固定 README](https://github.com/ActivityWatch/activitywatch/blob/b424aa61bfd4e9338c51dc53532bb7f6d3e275ed/README.md)描述本机采集活动窗口、应用名称、浏览器标签标题与 URL、AFK 状态；按 bucket 保存事件，通过 REST/query API 汇总，并提供 JSON 导出。它适合回答「最近在做什么类别的事情」「某日电脑使用时间」，不能仅凭窗口标题断言用户实际工作内容，也不覆盖健康、位置或可靠日程来源。文档列出 Windows/macOS/Linux/Android，未列出 iOS 支持。

**源码证据。** 总仓固定了 `aw-server@67cfb479a9f8511ad3a9595224cb22c35b9dbe65`。其 [api.py](https://github.com/ActivityWatch/aw-server/blob/67cfb479a9f8511ad3a9595224cb22c35b9dbe65/aw_server/api.py)有 bucket 与事件导入/导出/删除、相同状态心跳合并、失效缓存和导入失败回滚；[config.py](https://github.com/ActivityWatch/aw-server/blob/67cfb479a9f8511ad3a9595224cb22c35b9dbe65/aw_server/config.py)默认绑定 localhost，API key 配置默认未启用，可设置 Bearer key，info 与 OPTIONS 有例外。以上是固定开发源码观察，不是本次部署验证，也不能推广到所有历史版本。

**接入建议。** 由本机受控连接器调用本地 API，将用户选择的分类与时段汇总上传 LifeOS 私有服务；首次也可导入 JSON。不要让公网访客直接访问 ActivityWatch 或把密钥放入浏览器。标题、URL、窗口名称、主机名默认不进入公开投影；公开状态采用用户确认的「开发/学习/休息」等标签。人工状态应有明确有效期，并能覆盖自动推断。采集停止后状态过期为「暂无近期更新」，不能无限延长最后一个心跳。

**删除语义。** ActivityWatch 能删除自己的 bucket/事件；LifeOS 导入副本需要独立记录来源 ID、批次与删除标记。LifeOS 本地删除不默认反向删除用户原始活动日志。自动同步中的删除传播与已导出的公开缓存撤回需单独验收。

### 3.2 OwnTracks：移动端位置采集与轻量存储

**可借鉴能力。** [固定 README](https://github.com/owntracks/recorder/blob/f202b5be11fc98097d69ef460c1753cffe8300be/README.md)说明 iOS/Android 客户端通过 MQTT 或 HTTP 上报；Recorder 存储为文件，提供 REST、WebSocket 与 `ocat` 导出，支持位置/轨迹等查询。无需外部关系数据库，适合把采集协议与展示分开。

**授权与限制。** 文档提供反向代理 Basic Auth、受保护 view 等配置，不应把开箱监听接口当作 LifeOS 公网只读接口。设备位置权限、后台限制、离线队列、上报频率和电耗依赖实际平台与设置，本次未实测。MQTT broker、移动端、Recorder 各自的配置与许可不等于单个 Recorder 的结论。

**LifeOS 取舍。** 有持续位置需求时，优先采用 OwnTracks HTTP 消息作为一种连接器输入；若已经运行 Recorder，则从服务端适配已有查询接口。不要仅为一个城市级状态卡搭建整个 MQTT 链路。保留时间戳、精度、设备/来源标识，但 SSID、BSSID、家庭区域等只进入私有数据；公开卡片采用明确的城市级或人工地点标签。原始坐标和轨迹都必须独立授权公开。

**导入与删除。** 可参考其 GeoJSON/GPX 输出与文件存储。文档里的 LMDB `DELETE` 是缓存/键值数据库操作，不能误称为完整轨迹删除 API；本次未核验它具备按日统一删除及缓存清理事务。LifeOS 应独立完成导入批次撤回、轨迹点删除、派生路程/地图数据清理，外部源的删除另行处理。

### 3.3 Dawarich：较完整的位置历史业务

**可借鉴能力。** [固定 README](https://github.com/Freika/dawarich/blob/2dc26c40dff1f2e4b6c7e22d78ab5a271c0e8957/README.md)涵盖 OwnTracks、GPX、GeoJSON、Google Timeline 等导入，行程、地点访问、城市/国家统计、地图轨迹和导出。地点访问建议需确认/拒绝的流程值得参考；照片位置聚合与家庭共享不属于 #37 的默认需求。

**源码证据。** [OwnTracks controller](https://github.com/Freika/dawarich/blob/2dc26c40dff1f2e4b6c7e22d78ab5a271c0e8957/app/controllers/api/v1/owntracks/points_controller.rb)进行有效 API 用户与点数检查，字段白名单仍包含 Wi-Fi、设备电量等敏感元数据；[ApiController](https://github.com/Freika/dawarich/blob/2dc26c40dff1f2e4b6c7e22d78ab5a271c0e8957/app/controllers/api_controller.rb)支持 API key 参数和 Bearer header。LifeOS 若适配，使用服务端 Bearer 头并避免把密钥写入 URL 日志。该控制器还包含云订阅/数据窗口分支，部署时必须核对 self-hosted 配置与选定版本，不能照抄云版套餐语义。

[Imports::Destroy](https://github.com/Freika/dawarich/blob/2dc26c40dff1f2e4b6c7e22d78ab5a271c0e8957/app/services/imports/destroy.rb)删除导入点、处理孤立轨迹、更新点数与统计，并逐批失效地图 tile epoch。这说明删除不能只删数据库主行而留下缓存或统计。此处仅检查源码路径，没有实际运行并发删除测试。

**LifeOS 取舍。** Dawarich 适合已有较大量轨迹历史的可选后端，或作为轨迹整理、导入撤回和地点确认的行为参考。不要复制整套地图导航、家庭共享与商业功能；综合看板先提供摘要与日级详情，精细地图按需打开，图层不得包含策略禁止的点。地图服务/瓦片及逆地理编码也会接触坐标，应在供应商和数据出境偏好明确后选型；不默认调用外部地理编码服务。

### 3.4 wger：健康指标建模与运动记录

**可借鉴能力。** [固定 README](https://github.com/wger-project/wger/blob/8f72cb2feba9f5f1cc40aa9855b185ab315a3cd8/README.md)以健身、营养、训练与身体记录为主要定位。当前开发源码比「体重记录工具」更丰富：[Category](https://github.com/wger-project/wger/blob/8f72cb2feba9f5f1cc40aa9855b185ab315a3cd8/wger/measurements/models/category.py)定义心率、静息心率、血压组合项、血氧、步数、距离与多种睡眠阶段；不应依据旧介绍说它完全不能表达这些指标。

**源码证据。** [Measurement](https://github.com/wger-project/wger/blob/8f72cb2feba9f5f1cc40aa9855b185ab315a3cd8/wger/measurements/models/measurement.py)保存来源、外部 UUID、值、时间、原始单位/设备附加信息，并以 category/source/external_id 唯一约束去重。[API views](https://github.com/wger-project/wger/blob/8f72cb2feba9f5f1cc40aa9855b185ab315a3cd8/wger/measurements/api/views.py)使用 IsAuthenticated 与 owner query，提供时区参数、按时/日/周/月聚合、点数约束和删除限制；计算项不能直接删除，因为后续重算会恢复。

**LifeOS 取舍。** 可借鉴有语义的指标、原始来源、去重键、分组测量、按时区聚合与计算项依赖。服务器模型出现 `apple`/`google` 来源不代表已经证明移动端可持续同步；实际 SDK、客户端版本和用户设备仍需验证。wger 的训练计划、食材库、健身用户账户不需要被整体引入，低频报告也不应硬塞进一个非负数值字段。

**导入与删除。** 若用户已有 wger 数据，再适配其带权限的 API；否则仅参考模型。保留原始与派生记录之间的关联：删除源样本应重建对应聚合，删除一个展示点不能让下一次同步悄悄复活。官方指标类别和计算项的特殊删除规则需转成用户可理解的状态，不机械照搬其错误文案。

### 3.5 Fasten Health OnPrem：低频医疗记录参考

**可借鉴能力。** [固定 README](https://github.com/fastenhealth/fasten-onprem/blob/36d92446884e9e20eda8d2b2a0a1115c9c57f7ef/README.md)定位个人/家庭健康记录，使用 FHIR，支持手工记录与外部导出的 FHIR Bundle。2026-02-13 的说明明确区分 OnPrem 与商业 Fasten Connect：开源 OnPrem 不能直接从医疗机构导入，不包含商业平台连接能力。穿戴设备支持在 README 中仍列为未来项。

[resource_fhir.go](https://github.com/fastenhealth/fasten-onprem/blob/36d92446884e9e20eda8d2b2a0a1115c9c57f7ef/backend/pkg/web/handler/resource_fhir.go)有 FHIR 资源列表、查询、更新、删除 handler；这一文件不能单独证明完整授权、附件擦除或审计行为，相关部署安全性未测试。该仓库已经归档，不建议作为新持续在线健康后端的默认依赖。

**LifeOS 取舍。** 参考「原报告—结构化检查项—时间趋势」关系和来源追溯；优先自行实现规模较小的检查记录模型。需交换医疗数据时再支持明确版本的 FHIR 子集与 Bundle 校验，不为首次手工录入实现完整 EHR 系统。报告缺少字段、单位不一致或不属于支持资源类型时保留导入错误，不伪造正常值。

## 4. 设备与标准接入边界

| 数据来源 | 已核验的官方能力 | LifeOS 落地方式与限制 |
| --- | --- | --- |
| Apple Health / HealthKit | [授权文档](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)要求逐数据类型申请权限，可随时改变权限；当前文档还描述限定历史窗口。应用不能可靠区分某些读取权限被拒绝与没有数据 | 需要具备 HealthKit capability 的设备端桥接应用或用户主动导出。不能让 Web 页面直接向 HealthKit 查询；空结果应写「未获取到数据」，不能断言用户没有相关健康记录 |
| HealthKit 后台通知 | [后台投递文档](https://developer.apple.com/documentation/healthkit/hkhealthstore/enablebackgrounddelivery(for:frequency:withcompletion:))要求相应 entitlement；频率是最多唤醒频率，部分类型有小时级上限，必须真机验证 | 后台通知触发增量读取与上传，加入断线补偿。24h 服务在线不构成秒级数据 SLA；桥接能力/OS 可用版本需随实施时 SDK 再固定 |
| Apple Health 手动导出 | [Apple 支持文档](https://support.apple.com/guide/iphone/share-your-health-data-iph5ede58c3d/ios)提供全量健康数据 XML 导出 | 可作最早可验证导入路线，先在私有端解析并展示预览；不要求上传到公共仓库。使用 XML 解析器，限制归档大小/文件数并禁用外部实体；导入成功不意味着持续同步 |
| Android Health Connect | [读取文档](https://developer.android.com/health-and-fitness/guides/health-connect/develop/read-data)说明通常仅能读取首次授权前 30 天，扩展历史需历史权限；后台读取还要对应功能可用且获得后台权限 | 需要 Android 端 bridge/受支持应用。只申请选定指标的权限；区分历史不足、权限不足、设备不支持和实际无样本，撤权后停止后续采集 |
| Health Connect 增量变化 | [同步文档](https://developer.android.com/health-and-fitness/guides/health-connect/develop/sync-data)提供 UpsertionChange、DeletionChange，删除事件仅含 record ID；令牌失效需恢复策略 | 保存来源 ID 与类型映射，逐类型同步游标、幂等 upsert、删除传播及断点恢复。文档中的仅前台示例不能覆盖新后台权限能力，能力判断以读取文档与运行设备为准 |
| Health Connect 聚合 | [聚合文档](https://developer.android.com/health-and-fitness/guides/health-connect/develop/aggregate-data)说明 Activity/Sleep 按用户设置来源优先级去重，其他类型不能一概套用 | 步数与睡眠不能把手机、手表、同步 App 的重叠样本直接相加；保留统计算法与来源版本，解释来源差异 |
| 日程 | [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)规定 iCalendar 的 UID、时区、重复规则及例外 | 首期可手工安排或选择日历文件导入；持续同步需确认用户实际使用的 CalDAV/提供商。重复实例使用 UID + occurrence identity，处理取消、移动单次事件、全天日期、DST；不抓取用户未授权的日历 |
| 检查结果交换 | [FHIR R4 Observation](https://hl7.org/fhir/R4/observation.html)区分测量值、缺失原因、参考范围、原文解释；报告通过 DiagnosticReport 关联检查项 | 借鉴结构，不宣称已兼容整个 FHIR；保存原报告单位与参考范围，不跨检验方法无条件比较，不由本看板生成诊断 |

Apple 与 Android 文档会演进，本文记录的是 2026-10-18 读取到的内容；没有把当前文档里的新能力假定为用户旧设备支持。官方健康 API 是平台能力，不能视为可复制进本仓的开源健康服务；实现时需要记录所用 SDK、最低系统版本和相应条款。

## 5. 建议的数据模型与接口职责

这是供统一架构设计采纳的概念模型，不在本调研阶段创建数据库或强制字段命名。

| 实体 | 必要信息 | 关键业务规则 |
| --- | --- | --- |
| DataSource | 来源类型、设备/连接器、授权范围、同步游标、最后成功与失败时间、来源时区 | 凭据仅在私有服务；最后同步时间不替代测量时间；连接测试不读取未授权范围 |
| ActivityInterval | 起止、来源、活动类别、人工/自动、置信依据、有效期 | 原标题/URL 保留在私有原始记录；AFK 与活跃不能重复累计；人工覆盖可撤销 |
| ScheduleEvent | 来源 UID、实例标识、起止/全天、时区、公开标题、取消状态 | 参与人、会议链接、私有描述与原地点独立于公开标题；重复修改要更新对应实例 |
| LocationPoint / Track | 时间、坐标、精度、来源、导入批次、处理状态 | 降精度在服务端发生；缺测区间不连成虚假的实际路线；禁止点不应通过折线端点推断泄露 |
| HealthSample | 指标语义、数值或类别、单位、起止、原时区、来源 ID、设备、修订号 | 不把空样本记为 0；支持迟到、重复、修订与源端删除；不同单位只按已定义换算处理 |
| ExamRecord / ExamItem | 检查时间、报告、机构/方法原文、检查项、数值/文字、单位、参考范围、原文异常标记、审核状态 | 眼科至少区分左右眼与不同测量项；视力与屈光度不能混成同一指标；附件默认私有，结构化项发布也不自动公开整份报告 |
| SharingPolicy | 面板/指标、是否公开、历史长度、延迟、时区、公开字段、位置精度、策略版本 | 默认不公开；配置与执行均服务端；缺少/非法策略拒绝生成该公开指标 |
| PublicProjection | 允许的字段、覆盖区间、截止日期、生成时间、策略版本、数据修订、过期时间 | 与原始数据隔离；公开详情、搜索、图表、下载遵循同一策略；不能从摘要返回原始记录访问凭据 |

数据流建议为：设备/手工导入 → 私有接入与校验 → 标准化记录 → 按指标去重/聚合 → 公开策略投影 → LifeOS 访客看板。管理员查询与公开查询使用独立响应字段，不能先把私有结果发送给浏览器再执行过滤。

高频序列按窗口提供有界数据点或服务端聚合，避免把全天全部心率样本随概览下载；保留完整私有原始数据是否必要、保留多久需明确。健康日常汇总与低频检查记录使用不同单位与展示尺度，不合成未经确认的「健康分」或「器官运行正常」状态。

## 6. 逐指标公开、时间窗口和撤回

### 建议语义

三个操作应分别表达：停止从来源采集、从 LifeOS 删除已保存数据、取消向访客公开。它们不能互相冒充，也不自动授权删除上游设备数据。删除/撤回动作需要显示将影响的时间段、导入批次、附件和派生统计。

用户例子包含「不展示今日数据」，建议日级面板使用明确的自然日策略；这是待综合 spec 固化的建议，不能悄悄解释为严格 24 小时延迟。

- 设 `today` 为策略时区的当前日期，延迟 D 天时，最新允许日期为 `today - D`；D=0 可以包含今日且标注未完成，D=1 排除今日，D=7 最新允许到七天前。
- 历史 H 天相对**允许的最新日期**向前计算，闭区间为 `[today-D-(H-1), today-D]`；「全部」表示不设最早日期，仍受延迟规则限制。
- 例：时区中的今天为 2026-10-18，H=3、D=1 时，只允许 2026-10-15、16、17。H=3、D=7 时，只允许 2026-10-09、10、11。H=1、D=7 仍能显示 10 月 11 日，不能因把历史窗口锚定今天而意外为空。
- 若用户需要严格经过 24/168 小时才公开，增加明确的时间间隔语义，按 `observedAt <= now-delay` 执行；不能与「隐藏今日」混用同一不明文案。
- 睡眠跨午夜时需采用一致的归属规则，例如起床日，并保留原起止；未完成睡眠段不生成最终日统计。轨迹与活动跨公开边界时切分/裁剪，不能让一条跨界区间把禁用日期带出。

### 公开最小字段建议

| 面板 | 可由用户开启的公开内容 | 默认保留私有的信息 |
| --- | --- | --- |
| 当前状态 | 人工确认标签、更新日期、有效期 | 原窗口标题、浏览器 URL、主机名、精确工作项目路径 |
| 每日安排 | 选定日程的公开标题/时间，或忙闲区间 | 参与者身份、会议 URL、附件、未经编辑的描述与精确地点 |
| 位置 | 人工地点标签或选定粗粒度位置；历史轨迹另开关 | 当前位置原坐标、家庭/工作区域、Wi-Fi、设备标识；轨迹默认不公开 |
| 日常健康 | 单个指标的日统计/趋势以及来源说明 | 其他健康指标、完整样本、设备身份、未授权日期 |
| 检查记录 | 逐条审核的结构化检查项与日期 | 身份号码、条码、联系方式、报告原件、病史备注；附件需单独明确公开 |

公开策略需在聚合前应用或采用严格隔离的合法聚合结果，避免「隐藏今日心率曲线却在平均值、计数、tooltip、地图瓦片里包含今日数据」。修改策略必须失效摘要、详情、下载、地图与服务端缓存。公开接口不得返回隐藏功能的精确记录计数、最后检查时间等旁路信息。

静态 Pages 本身不能强制已经下载文件的撤回，也不能直接承载私有管理员原始数据。生产实现需要明确的长期服务与公开投影接口；如仍使用静态导出，必须显著说明数据截止时间、发布/撤回延迟，并避免把敏感原始数据写进 Git、构建产物或历史发布快照。公开过的数据可能已被访客保存，此限制应在首次公开确认中准确说明，不承诺追溯擦除第三方副本。

## 7. LifeOS 界面建议

综合看板内提供活动、位置、日常健康、检查记录的导航，沿用 daedalOS 窗口、工具栏、状态栏、字体、选中态、滚动条和紧凑中性表面，使用既有 Surface；不嵌入第三方 App 外壳，不复制其品牌侧栏或独立皮肤。

概览采用小型指标与最近更新时间，点击进入趋势或记录详情。时间范围只控制阅读；共享策略与数据源配置进入 OS 系统设置的管理区域，避免把普通应用默认加入设置按钮。中英文词条、键盘焦点、窄窗口自然换行/滚动沿用现有应用规则。

必须呈现「未配置来源」「等待授权」「尚无数据」「部分数据」「正在同步」「来源离线」「数据过期」「导入失败」等不同状态。公开访客只看到可公开的状态描述，不看到内部服务地址、授权原因、原始异常栈或私有指标列表。管理员能看到数据来源、最后成功时间、失败原因与重试入口。

## 9. 可观察验收条件

1. **逐指标权限**：心率公开、步数私有时，访客响应、图表、搜索、下载、错误响应和构建目录均无步数记录及私有身份字段；管理员可正常读取。未经授权的写入被服务端拒绝。
2. **边界日期**：固定 2026-10-18 的策略时钟，验证 H=1/3/30/全部与 D=0/1/7 组合，包括上述日期例子、午夜切换、DST 与更换时区；并记录自然日/持续小时模式的差异。
3. **原始与聚合一致**：隐藏日期不进入总数、平均值、最大值、tooltip、地图瓦片或 CSV；跨边界活动/睡眠/轨迹按已定规则处理。
4. **重复和修订**：同一来源 ID 重复导入/重试不增加步数或重复报告；修订更新既有样本；多个来源重叠按明确优先级处理，不盲目累加。
5. **新鲜度**：桥接停止、手机离线、设备未佩戴、权限撤回均不生成新的测量值；界面区分无数据、旧数据、采集中和错误，展示测量与接收时间。
6. **健康语义**：无样本不显示 0；单位、睡眠跨午夜、左右眼、血压组合项正确；异常标记来自报告原文并注明来源，不输出诊断、器官健康结论或擅自生成正常范围。
7. **导入失败与撤回**：损坏 JSON/XML、错误单位、超限归档、格式版本不支持时给出明确错误；导入预览不自动发布。整批撤回清除关联派生记录且保持其他批次。
8. **删除与缓存**：删除源记录/撤销公开后，公开摘要、趋势、详情、下载、地图与缓存一起更新；上游重新同步不无提示恢复本地刻意删除的数据；本地删除不默认删除设备原始数据。
9. **位置保护**：公开降精度结果中无原经纬度、SSID/BSSID 与设备 ID；禁用地点/日期不能通过路径连接、边界点和访问统计泄露；地图源与地理编码请求符合已确认范围。
10. **日程行为**：全天事件、跨时区事件、重复事件的单次取消/移动可正确导入；公开标题和忙闲视图不泄露原描述、参与人及会议链接。
11. **界面接入**：同一综合看板进程内可以导航上述面板，中英文、键盘、错误/空/加载态可用；窗口最小化/恢复/缩放与其他应用一致，不新增独立移动外壳。
12. **真实设备与运行**：选定连接器以实际授权设备验证后台读取、断网补发、重新授权、游标恢复、数据删除和服务重启；未测试平台明确列出。没有此证据不能把「24h 智能穿戴联动」标记完成。

## 10. 仍需确认的输入

- 手机与穿戴设备品牌/型号、系统版本、当前健康数据所在 App，是否已有 HealthKit/Health Connect 数据；未得到答案前不承诺覆盖全部指标。
- 当前日历与活动记录来源，是否已有 ActivityWatch、OwnTracks、Dawarich 或 wger 部署。已有来源优先只读接入，避免制造重复采集。
- 「实时」期望是状态分钟级、小时级趋势还是每日总结；实际频率受来源与系统约束，须经设备测试才能形成服务目标。
- 日级延迟与严格经过 24/168 小时的具体偏好；睡眠归属日、旅行时区与长期默认时区。
- 哪些指标可能公开、位置希望公开到何种粒度、是否公开历史轨迹；默认应全部私有，由用户逐项决定。
- 数据保存位置、原始样本/报告保留期限、备份方式与公网服务运行条件；此研究不授予购买资源、迁移真实健康数据或部署生产的权限。

## 11. 复用与交付边界

本次仅比较官方功能、读取部分实现并提出 LifeOS 行为要求，没有复制候选 UI、源文件、运动数据库、地图素材或文档正文。后续若引入具体库/代码/数据，需要逐项核对对应固定版本的 LICENSE、依赖与署名，不能只看项目主页的许可证徽章。当前优先独立实现本 OS 界面，通过可替换的数据连接器接入第三方服务。

本报告完成的是资料与源码层面的研究；没有运行候选服务、上传个人数据、修改 Issue、创建生产连接器、构建应用或发布。对比中的已实现能力仅指上游一手资料/固定源码所示，LifeOS 的实施与验收需要另行记录。
