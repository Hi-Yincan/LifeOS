2026-10-18 · v0.1 · 关联 [综合看板 #36](https://github.com/Hi-Yincan/LifeOS/issues/36)。这是实施规格与调研交付，不代表业务代码、真实连接器或生产后台已经完成。五份专题报告经独立审查后形成本规格；专题中的候选建议如与本文及 [架构契约](architecture.md) 不同，以综合规格明确收敛的语义为准。用户后续确认的设备、公开范围和运行条件继续更新本规格。

入口：[架构与隐私](architecture.md) · [验收矩阵](acceptance.md) · [任务与阶段](implementation.md) · [调研交接](../development/dashboard-research.md)。既有 [OS UI 规范](../concept/design-system.md)、[内容权限](../concept/data-and-permissions.md)、[Pages 规范](../deployment/pages.md)继续适用。

**当前实施范围更新（2026-10-18）：** 用户要求前端使用模拟数据，并已取消 LifeOS 管理员功能。所有人在 LifeOS 中读取相同内容；内容编辑、认证、凭据和发布转到独立信息源系统。当前交付及验收以 [前端设计与演示规格](frontend.md) 和 [信息源管理报告](../architecture/source-managed-content.md) 为准。本目录此前架构、验收和实施计划中的单密钥登录、App 内编辑及角色投影已被新决定替代；真实 API、持久化、采集与提醒仍未实施。

## 1. Executive Summary（概述）

**问题。** 作者的个人活动/健康、会员、服务可用性和服务器指标分散在不同来源；单个来源的界面与 LifeOS 不一致，权限、更新时间和统计口径也不同。把几套页面拼在一起不能保证数据可信或隐私一致。

**方案。** 新增一个原生 React 应用 `Dashboard`，以“总览 / 个人 / 服务”组织一级导航；服务栏目下包括“自建服务 / 服务器 / 会员看板”。共享来源、时间与公开投影，保留各领域独立模型。成熟开源项目提供业务与接口参考，采集后端按实际来源选配，界面使用 LifeOS 现有窗口、控件与主题。

**成功条件。** 以下是功能验收门槛，不是已测量的用户收益或性能承诺：

1. LifeOS 可阅读会员权益、续费计划和实际付款，来源和口径明确；建档、修改和实际处理确认由独立信息源系统承担，其真实能力单独验收。
2. 验收集中列出的私有哨兵字段、禁止日期和未经授权实体在公共响应、统计、媒体及导出中出现次数为 0。
3. 所有可见观测能解释来源、时间依据、单位与新鲜度；无来源、缺失、未知、陈旧和业务故障具有不同结果，无虚构样本或伪造实付。
4. 同一实例中五视图、中英双语、键盘、深链接、窗口操作和适用的本地/静态模式通过本次实际浏览器验证。
5. 只有所选来源完成认证、真实读写边界、断流/恢复和版本兼容测试后才标记“已接入”；只有独立运行和恢复证据齐备后才标记“24h 采集/可靠提醒”。

### 一手研究与取舍

| 领域 | 研究与证据 | 综合规格采用的方向 |
| --- | --- | --- |

## 2. User Experience & Functionality（使用与功能）

### 用户与入口

LifeOS 没有管理员身份和内容编辑，所有浏览者无需账户且读取相同展示数据。站长在独立的信息源系统维护记录；来源可采用已有管理界面或独立前端。采集器的机器身份由源系统约束，不将凭据传入 LifeOS。

一个 `Dashboard` 进程、一个窗口；开始菜单、商店和显式 `?app=Dashboard` 打开同一实例。首阶段不自动增加多个模块桌面图标；默认桌面是否新增单个看板快捷方式保留为入口任务的可选项，不能影响 Portfolio/App Store 和现有桌面排列。无参数访问仍显示桌面，不自动启动看板。

系统设置仅提供本机语言与时区。源端认证、连接器凭据、通知通道、记录编辑、导入确认及续费处理均在独立系统完成；LifeOS 不增加这些入口，也不保存其管理会话。

### 统一窗口结构

工具栏包含返回与当前位置，栏目及个人子栏目竖向排列；内容区是紧凑列表、摘要、趋势和详情；状态栏说明示例状态及数据时间。图表有单位、图例、缺口说明及可读表格替代；颜色不能是唯一状态标识。内容按窗口宽度自然排列/滚动，不检测设备类别，不强制全屏，不引入第二套移动导航。

总览显示统一展示数据中的摘要与待处理事项，并可进入相应实体详情。共用服务器/服务引用只连接实体，费用由会员计划唯一计算，不重复累加。首阶段模块顺序固定、查询在各模块内进行；跨域搜索、拖拽布局、任意 widget 脚本和插件商店不进入基础框架。

### 用户故事与完成条件

| 用户故事 | 可观察完成条件 |
| --- | --- |
| 作为作者，我要先看到近期需要处理的事，方便决定接下来做什么 | 总览只聚合合法数据；会员待核对/临期、来源异常和服务事件各有类别与详情入口，旧健康数据不被打分为异常；无数据有说明 |
| 作为浏览者，我要看懂会员权益、计划与实际付款 | 三者分别展示；源系统负责更新与处理确认；实付仅来自明确记录，未知金额不作为免费 |
| 作为浏览者，我要查看服务目录和监测结果 | 没有监测器仍可读目录；状态注明方法/位置/时间；采集失败不改写目标健康；维护和 pending 不丢失 |
| 作为作者，我要查看服务器资源及来源状态 | 单位/分母/采样窗口清楚；无样本不置零；历史断流保留缺口；凭据与远控入口不进入浏览器 |
| 作为浏览者，我要查看活动、日程、位置和健康记录 | 使用统一展示数据；保留来源、测量时间与缺口；纠错在来源进行，LifeOS 无编辑器 |
| 作为站长，我要在独立来源维护内容 | 源端认证和发布单独验收；返回 LifeOS 时与其他人展示相同；旧草稿与管理字段不自动公开 |
| 作为访客，我要看懂公开内容且无需账户 | 看不到私有数据或隐藏数量；明确这是实时来源、陈旧观测还是固定快照；不可访问对象使用一致不可用响应 |
| 作为作者，我要在页面关闭时仍能采集和提醒 | 仅在常在线服务与所选设备/渠道真实验收后提供；本地记录和 Pages 阶段准确标明边界 |

### 模块功能边界

**个人。** 活动/日程、位置/轨迹、日常健康、检查记录为四个子视图。高频指标包含睡眠、心率、步数等；低频包括体检、血常规、视力/散光。保留时间范围、单位、来源、空洞和附件。检查异常说明来自报告原文或人工记录，不生成诊断/治疗建议或器官健康分。设备来源尚未确认，不能承诺全平台实时同步。

**会员。** LifeOS 提供搜索/分类/排序、权益、计划、待处理、付款历史、原币汇总与明确口径的费用折算。关闭续费可保留权益；试用后价格未知单独标记；赠送/附带权益不重复计费。外部服务商链接只打开网页，不证明取消或付款已经发生。建档、付款确认和续费修改在独立源端实施。

**服务。** 服务稳定 ID 与访问入口、监测目标、上游 monitor ID 分离。多探测位置逐条展示或使用源配置的主检查，不将简单平均 uptime 当全球可用性。当前 90 日状态条使用明确标记的合成历史；未来来源不提供历史时不伪造曲线，按实际协议处理 pending/maintenance。

**服务器。** 首阶段只读主机列表、CPU/内存/文件系统/网络、来源和历史。GPU/容器/SMART/进程、WebSSH、远程命令/文件/部署、云账单分别是独立后续范围。Grafana 可作为作者已有高级运维入口，不构成此 App 的 UI 依赖。

### Non-Goals（本阶段边界）

不建立新的访客账号或独立商业订阅产品；不统一自动取消会员或接入银行；不做完整记账/EHR/训练平台；不实现任意代码 widget；不假定已有生产数据库、设备 bridge 或通知服务；不改变域名、购买资源、迁移真实个人数据或安装服务器 agent。

## 3. AI System Requirements（AI 能力）

首阶段不引入 AI 推断、OCR 或自动健康解释。导入与来源适配采用明确解析器和人工确认；未来若需要截图/报告识别，须独立定义数据去向、保留期、人工确认和错误验收，再建立 Issue。本规格不依赖模型调用或新增模型密钥。

## 4. Technical Specifications（技术要求）

当前边界见 [信息源管理报告](../architecture/source-managed-content.md)。原始数据、业务记录、派生聚合和展示输出由源端分层，LifeOS 只读取同一份展示结果。旧 [architecture.md](architecture.md) 的领域时间与来源研究仍可参考，其 LifeOS 管理接口与角色设计已取消。

时间显示至少区分测量 `observedAt`、源快照 `sourceUpdatedAt`、接收/获取时间与本次响应生成。未知测量时间可空，不能以刚抓取冒充刚测量。业务故障与 freshness 分开；来源能力不支持历史/单位时显式说明。

时间范围区分日历日与滚动时长，固定 30 天不能标成“1 个月”。当前前端不执行逐项公开、延迟或身份过滤；全部示例可读。实际来源若需要保留期或延迟处理，应在源端定义，不能以浏览器隐藏数据替代。

LifeOS 内本地编辑路线已取消；#31 的数据导出与旧内容处理需按独立源端方向继续核对，不在本轮迁移真实数据。静态 Pages 只接收明确可公开的固定内容；需要自动过期或更新的数据出口必须明确缓存与传播限制，已下载副本无法远程收回。

复用现有 TypeScript/React、Yarn 锁文件、Surface 和窗口系统，不附带全仓重构或依赖升级。领域类型不塞入 Portfolio 根 Provider。源码接入点与所有者划分见平台报告及任务计划。

## 5. Risks & Roadmap（风险与路线）

| 阶段 | 可用结果 | 退出门槛 |
| --- | --- | --- |
| R0 研究与规格 | 五专题研究、统一规格、Issue 目录和验收 | 独立审查、来源核验、时间/权限语义一致；不以代码或发布完成标记 |
| R1 只读前端 | 一应用五视图、统一展示模型、正确空态、时间与金额计算 | 当前合成前端验收；全量样本、中英文、导航与窗口操作，无隐藏管理实现 |
| R2 独立源端与读取契约 | 源端维护、鉴权、存储、公开 JSON/API 与 LifeOS 适配 | 后续单独实施；真实授权、版本冲突、字段白名单、恢复及缓存传播，不以合成数据证明接入 |
| R3 逐个连接器 | 按实际设备/现有服务交付至少所需连接器 | 固定运行版本、真实协议、权限、去重/修订/删除/断流恢复；未选平台明确待接 |
| R4 常在线与提醒 | 独立运行、持久存储、可靠调度/事件/一个确认通道 | 关闭网页/重启/异常恢复、缓存撤回、备份与来源隔离；设备频率及送达实际验证 |
| R5 发布 | 经授权的静态公开内容或动态出口上线 | 完整模式回归与回退，不因旧代码恢复而放宽隐私，记录设备/网络限制 |

主要风险是来源 API/权限变化、设备后台限制、时间/币种口径、静态副本无法撤回、原生 App 同源代码执行和长期数据恢复。对应控制已进入专门验收；不以时间估算、星数或 README 宣传替代验证。

实际设备/数据源、业务时区、展示字段、保留期与源系统位置继续登记，在对应实施阶段再确认。当前保留确定性的只读前端，不从运行目录推断用户决定，也不在本轮追问或开发源系统。
