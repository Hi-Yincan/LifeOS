## 复用原则

已将验证过的原型按模块迁入根目录产品工程。保留当前概念分支、规格与证据快照作为评审和回归参照；后续新 App 延续已经确认的 daedalOS 视觉与接入方式。正式工程成为后续唯一的功能实现来源，避免长期维护两套同步演进的代码。

| 原型资产 | 正式开发中的处理 |
| --- | --- |
| Portfolio / AppStore / SystemSettings 页面、原生工具栏与图标、窗口入口、双语词条、状态反馈 | 复用交互和实现；迁入正式目录，补全组件边界、类型、无障碍与长期维护规范 |
| 双语正文、已发布快照与媒体读取边界 | 保留统一展示契约；所有人在 LifeOS 读取相同内容，不读取旧草稿和私有字段 |
| 内容服务、单密钥认证与编辑实现 | 正式产品已退役认证和写入，仅保留本地只读服务；源侧管理方案独立研究 |
| 本地 JSON 文件、旧会话、原型运行目录、测试密钥与上传样例 | 保留既有数据，不自动迁移、删除或公开；新产品不创建或读取管理密钥 |
| AppStore 本机 URL 清单与 localStorage 模型 | 保留为待评审实验。正式实现前确认用户自建/站长发布边界、安装语义、包或 URL 接入、权限、版本与更新机制 |
| prepare.mjs 字符串补丁与临时 daedalOS checkout | 用于证明接入点和复现基线；正式集成按 #10/#11 决定仓库与上游同步方式，建立稳定接入点及升级回归，不依赖临时 checkout |
| 自动测试、布局探针、图像和验收矩阵 | 迁移能覆盖真实行为的检查；补齐 CI、原生应用分类回归、真实设备/网络和生产环境验证 |
| GitHub 项目文案、个人资料、项目媒体 | 继承已有来源记录；作者未提供的贡献细节、履历与媒体继续核验，不将研究草稿默认为正式公开内容 |

## 下一阶段顺序

1. 冻结概念规格与原型基线，整理变更及未决事项。
2. #21 已落实仓库/上游策略；在 #3 继续明确生产部署与内容服务边界，并逐模块确认复用、重构或替换。
3. 将 T01–T16 拆成开发 Issue，给出依赖、验收标准、迁移范围和证据要求。
4. 在 #21 已建立的正式 daedalOS 源码与回归基线上，逐步替换本地开发存储与服务，补齐生产能力。
5. 生产能力通过相应验收后再安排发布。当前草稿 PR #16 不因概念收尾而自动合并或上线。

## 本次桌面入口补充

App Store 与 Portfolio 均生成开始菜单和桌面快捷方式；二者分别指向已有单实例进程。所有原有桌面入口保留，排列交给 daedalOS 原生规则。默认进入桌面，作品集和商店均不会自动打开；显式 App 深链接仍可启动对应应用。

桌面入口和开始菜单入口打开同一个 AppStore 实例，不增加键盘组合键。快捷方式、文件系统索引和快捷方式缓存一起参与构建；浏览器中实际验证双击与单实例恢复。
