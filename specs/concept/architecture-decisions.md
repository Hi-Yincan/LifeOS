# 架构决策与依据

版本：1.0 概念交付稿。D-001（daedalOS 底座）与本轮产品范围来自负责人确认；以下为依据研究原型形成的实施建议，提交统一评审。未创建新 fork、submodule、付费资源或修改现网 DNS。

## ADR-01：只新增一个业务 App，保留全部原生 App

**决定：** v1 新业务仅为个人作品集。系统设置、多语言、多端导航是支撑能力。上游基线的 33 个应用/进程条目原样保留，含系统对话框；实际能在各设备运行的范围用清单验证，不把“条目保留”等同“所有功能通过”。

**原因：** 用户明确喜欢现有 App，目标是精进一个可作为后续参考的作品，而不是裁成仅剩博客的轻量桌面。

**后果：** 不执行先前可能考虑的通用 App 大裁剪；改为测量懒加载、首屏和后台资源。重型游戏、虚拟机、AI App 的移动表现和外部依赖保留例外记录，需要移除时另向用户确认。

## ADR-02：v1 优先在产品集成分支维护源码，不直接采用“脏 submodule＋覆盖脚本”

**建议：** 保留完整上游历史，以固定 SHA 建立产品源码基线，个人 App 和通用系统适配集中维护。独立底座 fork/submodule 继续作为后续可复用模板的演进方案，不把未验证的包化改造作为 v1 前提。

**依据：** daedalOS 是完整 Next.js 站点。实际研究原型需要集中修改应用目录、Provider 装配、首页系统适配、窗口按钮/关闭保护和元数据；并没有现成可以把任意外部 App 包无修改注入的稳定库 Interface。原型的 overlay 是可复现的研究工具，会修改实验 checkout，不能冒充符合 #11“子模块工作区不需手工改动”的生产集成方案。

**替代方案：** 独立 fork 暴露明确的应用/配置 Interface，再以 submodule 或版本包消费。这有利于多个真实站点复用，但需要额外设计、跨仓发布和兼容验证；当前用户确认先做个人站、以后再模板化，收益尚不足以要求提前全面框架化。

**实施约束：** 当前产品仓库有独立初始历史；首次引入使用专用分支并保留上游 ancestry 与来源，不能强行覆盖 main 或丢失既有研究记录。计划阶段明确导入/合并方案，常规升级走独立 PR。若负责人最终选择双仓，则以相同验收任务重新验证组合构建，而不是只添加 `.gitmodules`。

## ADR-03：桌面外壳与内容服务分离

**建议：** 前端静态导出，内容 API 独立部署；生产内容建议使用 PostgreSQL，媒体使用 S3 兼容存储。单作者会话先放数据库，多个 API 实例共享，不为了形式引入额外 Redis 服务。

**原因：** 原生浏览器文件系统属于访客侧工作空间，不能作为所有访客共享的作者发布库。持久数据独立于前端部署和 API 实例，才能可靠实现草稿、发布、媒体与后续多节点。

**限制：** 原型使用 Node HTTP＋本地文件＋内存会话，只验证关键行为。不能直接把它扩成公网生产后端，生产数据库事务、迁移、上传实际解码和会话撤销另有实施任务。

## ADR-04：单密钥管理，不建立账户系统

**决定：** 设置内折叠“站点维护”，输入一把作者密钥，不要求用户名。服务端验证后签发有期限会话，前端按会话显示编辑操作。

**要求：** 密钥不写入静态资源、URL 或 localStorage；生产 HTTPS、HttpOnly Cookie、限速、CSRF、Origin 校验、会话撤销与密钥轮换。发布/下架使用版本控制；UI 隐藏不能代替这些检查。

**待实施的安全门禁：** 全部原生 App 保留时，需检查同源脚本执行、文件导入和外部嵌入。若这些能力使作者管理会话暴露给不可信内容，则把管理编辑区域放入独立 origin，并在原生窗口内嵌入，仅交换必要状态；不能在未检查前声称各 App 已隔离。此检查不会通过无提示删除原 App 来解决。

## ADR-05：保留 hyc.ac 与当前 Pages 解析，先设计 API 多节点

**决定：** 正常访客一直通过 hyc.ac 访问，当前不改根域名 A 记录。额外域名/子域名可作为后台资源候选，但命名和启用必须在实施时核对现有占用。

**建议：** 发布同一版本 API 到可健康检查的多个节点，共享一致内容与会话；初期采用明确单写权威库，跨区只读/缓存或备用实例按延迟与一致性验证扩展。额外 CDN 不是必选项。

实施时优先核验未占用的 `api.hyc.ac` 等同站子域名，新增 API 解析与根域名 A 记录分开。前后端跨 origin 时显式配置 credentials、允许的 Origin、HTTPS Cookie 与 CSRF；若改用其他独立域名，还须验证跨站 Cookie 限制，不能照搬原型的同源请求。具体域名尚未配置。

**限制：** 根入口仍依赖 GitHub Pages，后端多节点不等于整站容灾。国内外速度、API 故障切换、数据库恢复与资源预算要实际测量，不能承诺“多台机器自然就近或永不中断”。新增 CDN 如需调整公开解析，作为独立变更评审并回归其他项目路径。

## ADR-06：语言、地区与内容版本分开

**决定：** 首发 zh-CN/en，浏览器匹配＋设置切换＋本地偏好；作品正文具有独立双语字段。字典按命名空间组织，后续语种通过添加资源扩展。

**原因：** UI 语言不等于地理位置、时区或服务区域；自动选择界面语言不能擅自翻译或修改作者原文。

**实施要求：** 公共 OS 文案与 App 文案分层；英文长度、中文断行、缺失翻译、地区格式与未来不同书写方向列入设计，不在 v1 声称所有旧 App 已完成本地化。

## ADR-07：按视口与输入能力适配三种显示模式

**决定：** 桌面保留多窗口，手机采用触屏全屏应用与系统导航，平板保留更适合大屏触控的侧栏和最大化应用。提供自动与手动覆盖，不将“Windows/Android/iPad”写成三个业务实现分支。

**原因：** 同一设备可能分屏、旋转或接入鼠标，UA 判断不能完整描述实际操作条件。三种表现共用数据、权限和 App 内容，不重复实现业务。

## ADR-08：静态兼容的内容直链先成立，分享元数据单独完善

**建议：** 首版保留根 query 形式的 OS 深链接，与原有 App 链接兼容。更丰富的分享页通过明确的静态发布构建生成，或另作服务端渲染方案评审；不在 Pages 环境依赖不存在的运行时重写。

**限制：** 当前原型的动态作品详情主要由客户端加载，没有证明每项作品独立 OG/SEO 已完成。公开内容发布后的网页缓存、静态分享元数据与 API 快照更新时间需有一致策略。

## ADR-09：概念完成不等于生产验收

交付必须包括可运行原型、两种布局、三端规则、实际测试证据、差异清单和计划任务。原型中的本地会话、文件存储、生成封面、DOM 渲染图和仿真设备都要标明适用范围。研究结论与产品决定有来源，缺失个人资料不编造；最终进入 #3 前由负责人统一评审。
