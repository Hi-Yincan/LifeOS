## C03｜底座 fork、个人站仓库与 submodule 的职责

日期：2026-10-16。状态：架构建议，尚未确认集成方式或创建仓库。daedalOS 作为二开底座的决定保持不变。

### 1. 对提出方案的判断

**独立维护一个 daedalOS fork 是合理的，尤其与“同时做可复用模板”的需求一致；submodule 可以作为源码集成候选，但需要先验证组合构建。** 不建议仅仅为了“备份”就增加一个承担运行依赖的仓库。

建议职责为：

```text
DustinBrett/daedalOS                 上游来源
        ↓ 受控同步
我们的 daedalOS fork                通用底座改动、必要适配、上游回归
        ↓ 消费经过验证的固定版本
Hi-Yincan.github.io                 个人品牌、内容 App、配置、部署

代码备份 / 内容库与媒体备份           分别覆盖恢复需求
```

这是拟议组织方式，不表示已创建 fork、配置 submodule 或完成通用框架改造。若最终只有少量个人改动，直接在一个产品 fork 中维护也可能成本更低；拆仓要通过实际复用与独立验证获得收益。

### 2. submodule 解决什么

Git submodule 让父仓库记录子仓库的位置和一个精确提交。个人站可以采用底座版本 A，独立验证版本 B，再用 PR 更新指针；底座更新不会自动改变已经记录的版本。[Git 官方说明](https://git-scm.com/book/en/v2/Git-Tools-Submodules)

但它不提供 React 接入、App 注册、主题注入或内容权限，也不自动解决上游合并冲突。它管理的是仓库关系，不是 Module 的 Interface。

daedalOS 当前 `package.json` 按完整 Next.js 站点构建，没有本次核验可见的 `main/exports` 库入口；`tsconfig.json` 路径映射指向项目根，构建脚本处理自己的 `public/`、搜索索引与文件系统资源。因此，把整个仓库放进 `vendor/daedalos` 并不会自然得到一个可供个人站导入的桌面包。

源码依据：[package.json](https://github.com/DustinBrett/daedalOS/blob/f017b393d4175eb396a741a7562299423843f1b1/package.json)、[tsconfig.json](https://github.com/DustinBrett/daedalOS/blob/f017b393d4175eb396a741a7562299423843f1b1/tsconfig.json)、[App 注册](https://github.com/DustinBrett/daedalOS/blob/f017b393d4175eb396a741a7562299423843f1b1/contexts/process/directory.ts)。这是接入成本判断，不是断言 submodule 方案不可实现。

### 3. 先定义接入处，再选择交付方式

将桌面视为 Module，它向个人站提供小而明确的 Interface。建议的 Seam 是“应用注册、站点配置与内容客户端注入”；这些是我们需要验证的设计，不是声称上游已经提供的稳定接口。

- 底座负责窗口、进程、任务栏及通用 App 容器。
- 个人站提供品牌/默认桌面配置、自有 App 定义和内容访问 Adapter。
- 身份、发布与私有数据授权由内容服务执行；不能把浏览器中的文件夹或 submodule 目录当作权限机制。
- 个人站不应散布针对底座内部文件的覆盖脚本；升级适配集中在已记录的接入处。

用默认演示配置与个人站配置两个实际构建验证这个 Interface 是否足够。如果每次新增衣柜功能都要修改底座内部、再修改父仓库复制脚本，拆仓没有降低维护成本，应调整 Seam 或暂用单仓维护。

### 4. 集成方式取舍

| 方式 | 收益 | 代价与适用条件 |
| --- | --- | --- |
| 产品仓库直接维护 fork | 开发、CI、提交最简单，沿用上游构建 | 个人改动与通用适配同仓；通过目录和小补丁控制混杂 |
| 独立 fork＋submodule | 保留完整源码、精确锁定版本；适合底座与产品分别评审 | clone/CI 需拉取子模块；跨仓修改须先发布子仓提交，再更新父仓指针；组合构建要自己定义 |
| 独立 fork＋版本化包 | 产品消费与升级清晰，可复用多个站点 | 需真实可构建的库入口、资源与样式契约、版本发布流程；不应为了形式先大规模 SDK 化 |

**建议先把独立 fork＋submodule 作为待验证方案，不立即将 npm 包化设为前提。** 通过验收后再决定是否采用；若收益不足，直接维护产品 fork 仍是有效备选，不影响已确认的 daedalOS 选型。

submodule 采用条件：

1. 干净克隆并递归取得固定提交后，能按单一文档命令构建个人站；CI 同样可复现。
2. 构建不要求手工修改子模块工作区，App 与品牌配置有明确接入处。
3. 底座从 A 升到 B，只需可解释的适配和指针更新；能跑通内容管理与访客流程。
4. 底座提交已推送且可访问，父仓库不引用仅存在于开发者本机的提交；团队/CI 的访问权限得到验证。
5. 父仓库回退版本能取回对应底座；数据迁移兼容仍按升级策略单独处理。

### 5. 备份是单独的恢复需求

fork 可保存代码副本与历史，submodule 可记录版本关系；它们不能代替完整备份方案。父仓库的 gitlink 不包含子仓库的 Git 对象；只保存父仓库不足以独立恢复底座。[Git submodule 文档](https://git-scm.com/docs/gitsubmodules)

恢复范围至少应分清：两个仓库各自的历史与引用、必要的大文件对象、Issue/spec 决策记录，以及数据库和媒体文件。代码版本控制也不包含线上内容的自动备份。同平台上的另一个仓库不覆盖平台或账户层面的全部故障场景。

本阶段先明确恢复范围；备份位置、频率、保留期限和恢复演练由生命周期任务细化。无需为了名称上叫“备份”而额外建立第三套运行代码仓库。

### 6. 本议题的完成条件

明确仓库职责、实际接入方式、固定版本与组合构建流程，并用两个底座版本完成验证后记录决策。上游差异检查、升级回归和回退政策由“上游同步与升级要求”议题负责；本议题只负责代码如何组织与接入，避免父 Issue 承载实施细节。
