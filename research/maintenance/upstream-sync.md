## C02｜daedalOS 上游同步与升级要求

日期：2026-10-16。关联：#2 概念阶段、#3 计划阶段、#6 生命周期阶段；承接已确认的 D-001 / R15。

状态：**PRD 补充建议，具体机制与节奏待概念/计划阶段落实。** daedalOS 选型保持已确认，#1 不重开。本记录没有执行代码导入、配置自动任务或升级现有产品。

### 1. 需要从首次二开就考虑

需要。应把“可持续跟进上游、可验证升级、可回退”作为非功能性要求，而不是等第一次冲突发生后再补救。

目标是复用上游的窗口、兼容性和缺陷修复，同时保持个人内容 App 与管理行为稳定。上游同步不等于每次提交自动进入产品；选定 daedalOS 也不代表其所有新增 App 或依赖都要在本产品启用。

- 上游有 `yarn.lock`；其已核验 CI 使用 Node 22，并执行构建、lint、单元测试与浏览器 E2E。运行环境和锁文件也应纳入版本基线。[上游 CI](https://github.com/DustinBrett/daedalOS/blob/f017b393d4175eb396a741a7562299423843f1b1/.github/workflows/main.yml)
- 当前本仓库仅有独立的初始站点提交 `efc0aefe2d8db4753c8b70ac9ea4d613f7232301`，不是已导入上游历史的 fork。首次引入要专门处理两边历史和现有文件，不能假定已经具备 fork 的同步关系。

以上是当前证据；未来上游若调整发布方式，可更新升级机制，不改变可追溯与回归要求。

### 3. 建议的代码组织

| 层次 | 建议 | 升级时的检查点 |
| --- | --- | --- |
| 上游桌面、窗口与任务栏 | 尽量沿用；必要修改保持范围清晰 | 对应上游差异、冲突、窗口/键盘行为 |
| 自有博客、衣柜等 App | 放在独立模块，通过应用注册与适配代码接入 | 组件参数、窗口生命周期、样式和内容链接 |
| 品牌、应用入口与默认内容 | 集中配置；统一标记需要修改的上游接入位置 | 上游是否更改注册、菜单、文件关联或预加载 |
| 身份与内容服务 | 独立维护业务 API、权限与数据模型 | API 契约、会话和发布权限，不依赖 OS 窗口状态判断权限 |
| 必须修改的核心逻辑 | 建立补丁清单，记录原因、文件和回归场景 | 上游是否已修复、补丁是否可删除或需重新适配 |

daedalOS 不是已承诺稳定插件 API 的独立框架包。这里提出的是本项目的隔离方式，不保证不修改上游文件或永远零冲突。应用目录等少数接入点仍可能需要直接维护。

精简无关功能时，也要区分“不展示”“不加载”“不打包”。先核验依赖和资源，再决定裁剪范围，避免大量无收益删除放大合并成本，也不能仅靠隐藏图标宣称已减小体积。

### 4. 建议的 Git 与基线机制

1. **保留可追溯的上游 Git 历史。** 首次引入在专用集成分支完成；处理现有站点文件并评审后，再形成产品基线。避免仅下载 ZIP 复制代码、丢失共同历史。
2. **区分上游跟踪与产品分支。** `origin` 为本项目，`upstream` 跟踪 DustinBrett/daedalOS；产品 `main` 仅接收已评审的变更。remote 的配置在实施任务中执行，本轮未变更。
3. **固定采用的 SHA。** 建议在 `UPSTREAM.md` 记录来源、实际集成 SHA、引入日期、运行环境、锁文件、对应升级 Issue/PR 和本产品发布版本。本次研究 SHA 不能冒充已经集成的版本。
4. **常规升级优先保留合并历史。** 在独立升级分支整合目标上游提交，解决冲突并验证，通过升级 PR 进入产品分支。避免把上游直接覆盖到产品工作区。
5. **自有功能与升级分开交付。** 升级 PR 以兼容适配为限，不夹带新的业务需求；既有产品分支不为升级反复重写公开历史。紧急单独移植的修复须记录来源，并在下一次整合时核对。

不预先要求引入 submodule/subtree；是否需要额外仓库结构由首次引入方案决定。当前目标是历史可追踪、差异可解释、升级可回退。

### 5. 一次升级的完整记录

`发现上游变化 → 升级 Issue → 独立分支与预览 → 回归与评审 → 合并/发布 → 更新基线`

每次升级 Issue/PR 至少记录：

- 当前实际基线与目标 SHA、采用原因和上游差异范围；目标 SHA 在评审中固定，不能始终指向移动中的 main。
- 窗口/进程接口、应用注册、样式、路由、存储、构建链和依赖锁文件的影响。
- 冲突文件、保留/删除/调整的自有补丁，以及裁剪后的应用和资源边界。
- 验证结果与未覆盖项：按变更范围运行上游检查，并覆盖本项目的应用打开/切换/关闭、公开内容直链和历史导航、小屏阅读与管理、admin 发布/下架及 visitor 越权拒绝等关键流程。
- 发布版本与可回退构建。内容/数据库迁移单独记录兼容性；回滚前端不等于回滚数据，涉及迁移时需先验证备份/恢复或兼容策略。

预览使用合成测试数据。验证不通过的目标版本不进入产品发布，记录阻碍并继续使用现有可用基线。

### 6. 节奏与自动化建议

- 可先采用**每周检查变化、每月评估常规升级**的节奏；这是建议，尚未创建定时任务或承诺固定升级日期。
- 与已启用功能相关的安全修复、严重故障和浏览器兼容性问题优先评估，不必等常规周期。
- 自动化适合发现提交差异、生成升级草案及运行检查；不默认自动合并或发布上游代码。
- 可选择暂缓某次升级，但应记录原因和下次复查时间，避免无意中长期脱离上游。

### 7. 纳入后续阶段的验收项

- **#2 概念/PRD：** 明确可维护性要求、关键用户流程与权限回归清单；接受哪些长期维护成本。
- **#3 计划：** 拆分首次引入、基线记录、补丁清单、CI/预览、升级与回退演练任务。
- **#4 开发：** 实现模块边界、升级所需检查及来源记录，避免为了实验便利扩散核心改动。
- **#5 验证/交付：** 用两个真实上游 SHA 做至少一次受控升级演练，验证代表性自有 App、冲突处理、回归和回退路径；不能把“无冲突 merge”单独视为验收通过。
- **#6 生命周期：** 维护实际版本、升级记录和待处理阻碍；持续跟进上游而不默认追随每个提交。

这项要求应在进入正式开发前落实到 spec 和任务拆分中。当前只补充记录，未改变已完成的产品调研决议，也未宣称上述机制已经实现。
